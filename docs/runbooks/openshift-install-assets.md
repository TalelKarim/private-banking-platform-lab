# OKD runtime installation assets

## Goal

This step turns the stable lab definition into **fresh, short-lived installer
assets** without creating any OKD node yet.

```text
cluster-config.yml
       |
       v
fresh install-config.yaml
       |
       v
openshift-install create manifests
       |
       +-- force mastersSchedulable=true for the 3-node compact cluster
       |
       v
openshift-install create ignition-configs
       |
       +-- bootstrap.ign
       +-- master.ign
       +-- worker.ign        (generated by installer, unused for this compact lab)
       +-- auth/kubeconfig
       +-- auth/kubeadmin-password
       |
       v
publish bootstrap.ign + master.ign
on okd-lb Nginx :8080
```

No bootstrap, control-plane or compute VM is created by this step.

## Why the installer uses `platform: none`

The cluster uses user-provisioned infrastructure: Terraform owns the OpenStack
network, ports, security groups, load balancer and, in the next phase, the Nova
servers themselves. The installer is therefore used only as the **asset
factory** and does not create infrastructure.

This keeps the responsibility split explicit:

```text
Terraform          -> OpenStack infrastructure
openshift-install  -> manifests + Ignition + cluster credentials
Ignition/SCOS      -> first-boot configuration of each future node
```

OpenStack-specific storage/cloud integration can be added deliberately as a
post-install platform exercise instead of giving the installer ownership of the
Nova lifecycle.

## Pull secret

The default lab path uses the documented OKD fake pull secret because the lab
does not require an authenticated private registry during bootstrap. A real
pull secret can be injected at runtime without touching Git:

```bash
export OKD_PULL_SECRET='<json>'
make prepare-okd-install-assets OKD_LB_FLOATING_IP=192.168.250.x
```

The secret is written only inside `.runtime/`, which is gitignored and mode
`0700`/`0600`.

## SSH key

The public key for the SCOS `core` user is derived from the workload private key
that the ops-runner already retrieves from SSM:

```text
/home/ubuntu/.ssh/private-banking-openstack-workloads
       |
       +-- ssh-keygen -y
               |
               +-- install-config.yaml sshKey
```

This means the existing secret-management path is reused and no new private key
is committed or placed in Terraform state.

## Three-node compact scheduler

The installer generates Kubernetes manifests first. Before generating Ignition,
the automation explicitly sets:

```yaml
spec:
  mastersSchedulable: true
```

because this lab has three control-plane nodes and **zero dedicated workers**.
Application workloads will therefore run on `okd-01`, `okd-02`, and `okd-03`.

## Runtime directory and certificate freshness

Generated assets live under:

```text
.runtime/openshift/install/
```

They are not source code. Installer-generated bootstrap certificates are
short-lived, so the automation reuses an asset set only when:

- the canonical cluster config / SSH key / pull-secret fingerprint is unchanged;
- the asset set is younger than 10 hours.

Otherwise the installation directory is deleted and generated from scratch.
This matches the lab's daily destroy/rebuild model.

## Publishing Ignition

Only the two large Ignition payloads required by the first cluster machines are
published:

```text
http://10.20.0.10:8080/bootstrap.ign
http://10.20.0.10:8080/master.ign
```

The files are copied over the existing management SSH path to `okd-lb`, stored
as `root:www-data` mode `0640`, then verified twice:

1. `sha256sum -c` directly on `okd-lb`;
2. download through Nginx and compare the served SHA-256 with the local source.

The HTTP port is restricted by the OpenStack security-group design to the lab
networks; Ignition is never committed to Git or written into Terraform state.

## Commands

Generate only:

```bash
make generate-okd-install-assets
```

Publish an existing fresh asset set:

```bash
make publish-okd-ignition OKD_LB_FLOATING_IP=192.168.250.x
```

Normal combined operation:

```bash
make prepare-okd-install-assets OKD_LB_FLOATING_IP=192.168.250.x
```

The normal daily path remains:

```text
Terraform AWS apply
  -> Terraform OpenStack apply
     -> make configure-lab
        -> ... existing services ...
        -> OKD DNS/LB
        -> installer + SCOS image
        -> fresh manifests/Ignition
        -> publish Ignition
```

## Validation

On `ops-runner`:

```bash
ls -la .runtime/openshift/install
cat .runtime/openshift/install/ignition.sha256

grep -n 'mastersSchedulable' \
  .runtime/openshift/install/manifests/cluster-scheduler-02-config.yml 2>/dev/null || true
```

The manifest directory is consumed by `create ignition-configs`, so the main
post-generation validation is the existence of `bootstrap.ign`, `master.ign`,
`metadata.json`, and `auth/kubeconfig`.

On `okd-lb`:

```bash
sudo ls -l /srv/okd/ignition
cd /srv/okd/ignition && sudo sha256sum -c ignition.sha256
curl -fsS http://10.20.0.10:8080/bootstrap.ign >/dev/null
curl -fsS http://10.20.0.10:8080/master.ign >/dev/null
```

## Next phase

The next phase creates the **secondary/stub Ignition configs** and the actual
Nova machines:

```text
bootstrap stub -> downloads bootstrap.ign from okd-lb
master stubs   -> download master.ign from okd-lb

Terraform OpenStack
  -> bootstrap 10.20.0.11
  -> okd-01    10.20.0.21
  -> okd-02    10.20.0.22
  -> okd-03    10.20.0.23
```

Only then does the real OKD bootstrap begin.
