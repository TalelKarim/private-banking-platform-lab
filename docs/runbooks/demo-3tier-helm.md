# demo-3tier Helm migration runbook

This runbook explains how the `demo-3tier` OpenShift application is now deployed with Helm.

## 1. Mental model

Before this patch, Jenkins deployed the application by applying raw YAML files:

```text
oc apply -f configmap.yaml
oc apply -f postgres.yaml
sed "s|__BACKEND_IMAGE__|...|g" backend.yaml | oc apply -f -
sed "s|__FRONTEND_IMAGE__|...|g" frontend.yaml | oc apply -f -
sed "s|__DEMO_PUBLIC_HOST__|...|g" route.yaml | oc apply -f -
```

That works, but it is not very clean once the application grows.

With Helm, the deployment becomes:

```text
Helm chart + values
        ↓
helm upgrade --install
        ↓
Kubernetes/OpenShift objects
```

A Helm chart is a package of Kubernetes/OpenShift manifests. It is not an application image. The application images still live in the OpenShift integrated registry. The chart lives in Git with the project source code.

## 2. New chart location

The chart is stored locally in the repository:

```text
applications/demo-3tier/helm/demo-3tier/
  Chart.yaml
  values.yaml
  templates/
    _helpers.tpl
    backend.yaml
    configmap.yaml
    frontend.yaml
    limitrange.yaml
    postgres.yaml
    resourcequota.yaml
    route.yaml
```

Meaning:

- `Chart.yaml` describes the chart itself.
- `values.yaml` contains the configurable values.
- `templates/` contains the real YAML manifests, but with Helm variables like `{{ .Values.backend.image.ref }}`.

## 3. What Helm manages now

The Helm release name is:

```text
demo-3tier
```

The namespace remains:

```text
demo
```

The Helm chart now owns these runtime resources:

```text
ConfigMap/demo-backend-config
Service/demo-frontend
Service/demo-backend
Service/demo-postgres
Deployment/demo-frontend
Deployment/demo-backend
StatefulSet/demo-postgres
Route/demo-3tier
ResourceQuota/demo-3tier-quota
LimitRange/demo-3tier-defaults
```

The following resources intentionally stay outside the chart for now:

```text
Namespace/demo
Secret/demo-postgres-credentials
ImageStream/demo-frontend
ImageStream/demo-backend
```

Why:

- The namespace and Jenkins RBAC are platform foundations.
- The PostgreSQL Secret is runtime-only and generated by `scripts/configure-demo-3tier.sh`; the password must not be stored in Git.
- ImageStreams must exist before Jenkins pushes images, so they remain applied in the image-push stage.

## 4. AMI-ready context

This Helm migration does not rebuild OpenStack or OKD.

When the lab is restored from the ready AMIs, the expected workflow is:

```bash
cd ~/private-banking-platform-lab
make validate-openstack
make recover-openstack-guests
make configure-openshift-cicd
make configure-demo-3tier
make migrate-demo-3tier-to-helm
make deploy-demo-3tier
make test-demo-3tier
```

Do not start with `make configure-lab` unless the AMI restore is broken and a full reconvergence is really needed.

## 5. First migration from legacy oc-apply to Helm

The existing demo resources were originally created by `oc apply`, not by Helm.

If Helm tries to install a resource that already exists but has no Helm ownership metadata, it fails with an error like:

```text
resource already exists and cannot be imported into the current release
```

The migration script handles this with a clean takeover:

```bash
make migrate-demo-3tier-to-helm
```

It deletes only the runtime resources that Helm will now own:

```text
Deployment/demo-frontend
Deployment/demo-backend
StatefulSet/demo-postgres
Service/demo-frontend
Service/demo-backend
Service/demo-postgres
ConfigMap/demo-backend-config
Route/demo-3tier
```

It keeps:

```text
Secret/demo-postgres-credentials
PVC/postgres-data-demo-postgres-0
ImageStreams
```

So PostgreSQL keeps its persistent Cinder-backed data volume.

## 6. Manual Helm render without applying

To only see the generated YAML:

```bash
make helm-template-demo-3tier
```

This runs the migration script in dry-run mode and prints the rendered manifests.

Equivalent raw command:

```bash
DRY_RUN=true ./scripts/migrate-demo-3tier-to-helm.sh
```

## 7. Jenkins deployment path

`make deploy-demo-3tier` still triggers the Jenkins job:

```text
demo-3tier-deploy
```

Inside the job, Jenkins still does:

```text
1. checkout Git
2. build frontend/backend images with Podman
3. push images to the OpenShift integrated registry
4. resolve immutable image digests from ImageStreams
```

But the final deployment is now Helm-based:

```bash
helm upgrade --install demo-3tier applications/demo-3tier/helm/demo-3tier \
  --namespace demo \
  --wait \
  --atomic \
  --timeout 10m \
  --history-max 10 \
  --set-string frontend.image.ref="$FRONTEND_IMAGE" \
  --set-string backend.image.ref="$BACKEND_IMAGE" \
  --set-string route.host="$DEMO_PUBLIC_HOST"
```

Important flags:

- `upgrade --install`: update if the release exists, install if it does not.
- `--wait`: wait until Deployments/StatefulSet are ready.
- `--atomic`: rollback automatically if the release fails.
- `--history-max 10`: keep a bounded release history.
- `--set-string`: inject values coming from Jenkins, especially immutable image digests.

## 8. Useful Helm commands

List releases:

```bash
helm list -n demo
```

Show the release status:

```bash
helm status demo-3tier -n demo
```

Show values used by the release:

```bash
helm get values demo-3tier -n demo
```

Show the final YAML stored by Helm:

```bash
helm get manifest demo-3tier -n demo
```

Show deployment history:

```bash
helm history demo-3tier -n demo
```

Rollback:

```bash
helm rollback demo-3tier <REVISION> -n demo
```

Uninstall the release:

```bash
helm uninstall demo-3tier -n demo
```

Be careful with uninstall: the StatefulSet is removed, but the PostgreSQL PVC normally remains. Validate before deleting any PVC.

## 9. ResourceQuota and LimitRange

This patch adds namespace guardrails for `demo`.

### ResourceQuota

`ResourceQuota/demo-3tier-quota` limits the maximum namespace consumption:

```yaml
pods: "15"
services: "8"
secrets: "20"
configmaps: "20"
persistentvolumeclaims: "4"
requests.cpu: "1500m"
requests.memory: 2Gi
limits.cpu: "3"
limits.memory: 3Gi
requests.storage: 10Gi
count/routes.route.openshift.io: "5"
count/imagestreams.image.openshift.io: "4"
```

Mental model:

```text
ResourceQuota = maximum budget for the namespace
```

### LimitRange

`LimitRange/demo-3tier-defaults` defines default requests/limits for containers that do not specify them.

```yaml
defaultRequest:
  cpu: 10m
  memory: 32Mi
default:
  cpu: 250m
  memory: 256Mi
min:
  cpu: 5m
  memory: 16Mi
max:
  cpu: "1"
  memory: 1Gi
```

Mental model:

```text
LimitRange = default/min/max per container
```

This is useful because the Jenkins E2E test creates a short-lived Pod with `oc run`. If that Pod does not specify resources, the LimitRange injects safe defaults.

Validate the policies:

```bash
oc get resourcequota,limitrange -n demo
oc describe resourcequota demo-3tier-quota -n demo
oc describe limitrange demo-3tier-defaults -n demo
```

## 10. What changed pedagogically

Before:

```text
Raw YAML + sed + oc apply
```

After:

```text
Helm chart + values + helm upgrade --install
```

So the chart becomes the clean deployment contract for the application.

The source code is still built by Jenkins. The images are still stored in the OpenShift registry. The runtime deployment is now managed as a Helm release.
